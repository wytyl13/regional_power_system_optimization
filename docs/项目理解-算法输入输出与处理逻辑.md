## 1. 这个项目在干什么（一句话 + 一段话）

一句话：给定一个省未来某年的电力系统（机组清单、负荷曲线、新能源曲线、规则参数），求解"每台设备每小时怎么运行"，使整个周期总成本最小。

一段话：输入三份 Excel（设备台账、逐时运行曲线、规则参数），算法用 Gurobi 建一个混合整数规划模型（MIP，下文简称"优化模型"），决策变量是每台机组每个小时的出力和开停机等，约束是物理运行特性（爬坡、最小开停机、SOC 等）和系统要求（功率平衡、备用、碳排放上限、新能源利用率），目标函数是六大类成本之和最小。输出是逐小时的运行方案 + 成本/电量等分析指标。技术文档《全部模型汇总-0929》的前半部分（目标函数 + 各电源运行模型 + 网络约束 + 系统级约束）就是这个优化模型的数学定义，后半部分（"模型输入与输出变量说明"）逐表列了每个变量的含义和单位。

结构分层：大区域 → 省 → 供需平衡分区。平衡方程建在分区层面，海南算例是单省单分区退化情形。

## 2. 数据流（一条线从模板到结果）

### 2.1 服务链路（用户视角）

```
模板.xlsx（前端上传）
  → parse_template.py   解析出结构化 dict（机组、曲线、检修等收资数据）
  → tree.py             生成前端展示树（categories：表格 + 曲线懒加载元数据）
  → defaults.py         config 表单 default + merge_config（用户改的配置和默认合并）
  → [用户提交计算 POST /api/jobs]
  → convert.py          模板 + 生效配置 → 三份中间表（就是算法的输入三件套）
  → power_opt           求解（见 2.2），产出 solution.json（views 供前端渲染）
  → GET /api/jobs/{id}/results
```

### 2.2 算法链路（power_opt 内部）

```
三件套 xlsx
  → reader.py            读公共输入（时间轴、分区、负荷/风光曲线、断面、省级约束、DR）
       └ model/units/*.py 各自 load_*() 读自己的机组台账
  → solve.py::build       8 类电源建变量/约束（units）+ 系统层（context.py：平衡/备用/CO2/利用率/断面）
  → solve.py::add_objective 六大成本项 + 分项成本表达式（4.1-4.14 一比一对照 MATLAB）
  → Gurobi solve          四项核对打印（变量规模/约束规模/求解状态/目标值）
  → solution.py::extract_all    取值 → SolutionData（纯数据）
  → solution.py::compute_metrics 派生指标（平衡残差、利用率、备用裕度…）
  → solution.py::write_result_json  结果.json（服务/前端口径）
  → analysis_export.py    五张分析表 + .mat + 摘要.txt + 7 张 PNG（MATLAB 八~十二节口径）
  → plot.py              设备运行堆叠图（全系统 + 分区）
```

## 3. 输入：三份表各管什么

| 表 | 管什么 | 人话 |
| --- | --- | --- |
| **分区机组信息表.xlsx** | **有什么设备** | 每类电源一个 sheet：煤电/气电/核电/生物质/抽蓄/电储能/常规水电/风电/光伏/友好电站 + 分区表 + 检修计划 + 煤电碳排节点。一行一台机组，含容量、爬坡、成本系数、SOC 参数等 |
| **运行数据.xlsx** | **什么时候用多少** | 逐时曲线 sheet：负荷-8760、风电/光伏可用出力曲线（按电站）、水电曲线（按水文年）、送电协议 |
| **算例系统参数.xlsx** | **按什么规则玩** | 系统参数（惩罚成本、成本折算系数）、省级约束（备用率、CO2 上限、新能源利用率下限）、省级参数（hotReserveRatio 等）、需求响应时序上限、区域检修、水电调节周期、省内断面、省间通道、煤电碳排节点 |

配置参数的生效优先级（convert.py 头注释）：用户 config 显式键 > Excel 收资值 > defaults.DEFAULT_CONFIG。

求解参数：T（时段数）、START_TIME、MIGAP、TIME_LIMIT、水文情景（平/枯水年）——服务场景下由用户 config 注入，命令行跑由 config.py 直接改。

### 5.3 网络与系统级（model/context.py，274 行）

| 约束族 | 技术文档节 |
| --- | --- |
| 分区功率平衡（发电+储能净出力+互济+失负荷=响应后负荷） | 系统级约束-功率平衡 |
| 省内断面（分区通道容量、双向限值） | 电网侧-省内互济 |
| 省间互济（海南关闭 USE_INTERPROVINCIAL=False） | 电网侧-省间互济 |
| 热/冷备用（周最大负荷 × 备用率，分 Province） | 系统级-旋转备用 |
| 省级新能源利用率下限 | 系统级约束-新能源利用率 |
| CO2 排放总量上限（煤+气） | 系统级约束-碳排放总量 |
| 需求响应（可转移负荷转移边 + 电量守恒、可削减日/年限额） | 用电侧协同模型 |
| 失负荷比例上限 | 切负荷约束 |

units 与 context 的耦合只经过 RegisteredUnits / SystemVars 汇总量——对不上数时按层定位（README 总纲）。

### 5.4 决策变量（输出侧真正关心的）

每台机组×每时段的出力 P、开停 u、启动/停机动作 v/w、备用 R；储能的充放功率与 SOC；系统层的弃风/弃光/弃水、失负荷 P_shed、需求响应三件（P_shift_out/in、P_cut）、断面潮流 P_line。完整清单见 solution.py::write_result_json 的 series dict（27 项）与技术文档后半"输出信息"表。

## 6. 服务侧六个端点（现状）

| 端点 | 干什么 |
| --- |
| POST /api/datasets | 上传模板 → 解析 + 校验 → datasetId + categories 树 + config 表单 + fixedParams + warnings |
| GET /api/datasets/{id}/curves/{sheet} | 曲线懒加载（服务端按 filterBy 规则收口筛选） |
| POST /api/jobs | datasetId + config → 校验 → jobId 入队 |
| GET /api/jobs | 任务列表（内存态 + 落盘历史混合，新→旧） |
| GET /api/jobs/{jobId} | 状态 + 四项核对（solved 时）+ report / error |
| GET /api/jobs/{jobId}/results | solution.json 全量（含前端 views） |

执行模型：单队列单守护线程串行（同时只解一个），前端轮询。状态机 queued → running → solved / failed（异常落 error.log）/ interrupted（重启遗留）。

## 7. 与 MATLAB 的关系（为什么代码里有这么多对账注释）

本项目从 MATLAB 移植而来，协议：一比一对照、四项核对（变量/约束规模、状态、目标值）、best bound 逐位一致 = 数学恒等硬证据。README.md 记录了九轮完整对账史与十三坑。**任何重构都不得改变模型数学**——改完必须跑 T24 回归对四项+obj（见黄金规则）。

## 8. 常用命令（power_opt/ 下）

```bash
python reader.py                    # 输入自测
python -m model.units.thermal      # 煤电层自测（各模块同理）
python -m model.context            # 系统层自测
GRB_LICENSE_FILE=/c/gurobi1300/win64/bin/gurobi.lic python solve.py   # 全模型求解
python compare.py <T> <MATLAB obj> # MATLAB 对拍
python plot.py <T> save            # 设备运行图
```

服务跑法：`service/` 下 `uvicorn app:app --port 8000`（conda env power_opt，需挂 GRB_LICENSE_FILE）。
